## 二、仓库、分支和推送

- **仓库是公开的。** 暂存时逐个写路径，不用 `git add -A` 或 `git add .`。代码、测试、文档和提交信息里不出现真实的机器地址、serverId、用户名、本机路径或实测数据，测试用 `tests/helpers/center.ts` 里的占位值。
- **不部署。** 不碰线上检出、线上数据库、launchd 和 systemd 服务、Paseo daemon 上已安装的插件。需要在真实 Paseo 里验证时，另起一个隔离的 daemon（独立的 home 目录和端口，用完删除），只在它上面安装插件。
- 两套检查都必须通过：
  - 根目录：`npm run typecheck`、`npm test`、`npm run build:web`
  - `plugin/`：`npm run typecheck`、`npm test`、`npm run build`

- 客户端只用 React Native 的原语，文字颜色取自主题。本期只改设置页。

## 四、已定的决定

不要重新讨论：

- **只装一台。** 插件只装在中心所在的机器上，它是数据库唯一的写者。其他机器不装插件，它们的数据经本机 daemon 的一跳连接读取。
- **采集范围。** 只采本机和登记在本机 daemon 上的机器。新登记的机器默认不采集，由用户在设置里打开。
- **已关闭的 session。** "读取已关闭 session 的内容"默认关闭（设置项已有）。
- **原文。** 对话文本永久保留，不脱敏。工具调用的详情（输入、输出、错误）受存储上限约束：默认 2 GB，设置里可改；超过后从最旧的开始清，只清已经处理过的。
- **数据库位置。** 默认 `~/.local/state/paseo-task-manager/<daemon 的 serverId>/task-manager.db`，配置可以覆盖。首次启动自动建库；建过库之后文件不见了就报错，不悄悄新建。
- **兼容入口。** 原来端口上的 HTTP（采集上报、`/mcp`、网页）由插件继续提供，外部的 MCP 客户端不用改。

### B0 中心在插件进程里运行

**目的**：插件服务端启动时运行整个中心，插件里的采集器直接在进程内把数据交给中心。

**改动**

1. **可启停的中心。** 新文件 `src/server/center.ts`，把 `src/cli.ts` 里 `runServer` 的装配逻辑拆出来。`runServer` 只剩读配置、处理信号、调用它。

   ```ts
   export type CenterOptions = {
     config: ServerConfig;
     /** Directory of the config file: provider secrets set from the web UI live beside it. */
     configDir: string;
     webDir: string;
     log: (line: string) => void;
   };

   export type RunningCenter = {
     db: DatabaseSync;
     port: number;
     /** Stops taking requests, waits for a model call in flight, closes streams, the HTTP server and the database. */
     stop(): Promise<void>;
   };

   export function startCenter(options: CenterOptions): Promise<RunningCenter>;
   ```

   `stop()` 可以重复调用。现在 `runServer` 的行为（日志、启动时检查令牌文件、模型调用结束后才关库）保持不变。

2. **单写者锁。** 打开数据库前，在数据库旁取一把锁。锁被另一个活着的进程持有时，启动失败，错误信息写明持有者的进程号和启动时间；持有者已不存在（例如机器重启后留下的锁）时接管。`src/paseo-collector/state-store.ts` 已经实现了能处理重启遗留锁的做法，把它抽成共用代码再两处复用，不要复制一份。

3. **插件入口。** `plugin/server/plugin.ts` 启动时调用 `startCenter`，清理时调用 `stop()`。中心代码由 esbuild 一起打进 `server/bundle.mjs`。带原生可执行文件的依赖（`@anthropic-ai/claude-agent-sdk`）保持外置，运行时从仓库根目录的 `node_modules` 解析；插件只支持从已在根目录执行过 `npm ci` 的检出、按路径安装。运行时只能有一份 zod：核对根目录和 `plugin/` 的 zod 版本，不一致时统一。

4. **进程内入库。** 采集器现在通过 HTTP 客户端（`plugin/server/collector/client.ts`）向中心申请租约、上报快照和批次、查询检查点。新增一个实现同一接口的进程内版本：直接调用 `src/server/ingest-repo.ts` 里 HTTP 路由调用的同一批函数，走同一个事务，不再需要 HTTP 和令牌。来源身份沿用数据库里已有的：按 daemon 的 serverId 找到 `ingest_sources` 里对应的 `source_id` 和机器名，检查点接着走，不能换新的来源 ID 从头读。离线暂存（outbox）的逻辑不变。

5. **配置。** 插件按本机 daemon 的 serverId 读取唯一的 `<config 目录>/paseo-task-manager/<serverId>/config.json`。它直接包含中心配置。连接地址和 serverId 从 daemon 运行信息读取，采集状态使用默认目录。移除旧插件配置及其中的来源和 token 文件绑定。

6. **去掉重复代码。** `plugin/server/protocol/` 是 `src/shared/` 的副本，删掉，插件改为直接引用 `src/shared/`。插件采集器补上阶段 A 的回合 ID（`plugin/server/collector/normalize.ts`），和根目录的采集器一致。根目录的 `src/paseo-collector/` 和 `collect-paseo` 命令仍有机器在用，本期不删，切换上线完成后另行删除。

7. **看门狗。** 插件进程崩溃后 Paseo 不会自动重启它（已实测）。在 `deploy/` 下加一个脚本和一个 launchd plist 模板：每 60 秒执行一次 `paseo plugin ls --json`，插件状态为 `failed` 时执行 `paseo plugin reload paseo-task-manager` 并记一行日志。模板里的路径用 `$HOME` 占位。

8. **manifest。** 插件的名称和描述改为反映整个中心，不再只说"采集"。

**测试**

| 文件 | 用例 | 预期 |
|---|---|---|
| `tests/server/center.test.ts` | 在临时数据库上 `startCenter` | `/status` 有响应 |
| 同上 | `stop()` 之后在同一个数据库和端口上再次 `startCenter` | 成功（端口已释放，库已关闭） |
| 同上 | 同一个数据库上同时启动两个中心 | 第二个失败，错误里有持有者的进程号 |
| 同上 | 锁文件属于一个已不存在的进程 | 接管成功 |
| 同上 | 连续调用两次 `stop()` | 不报错 |
| 同上 | 一个模型调用（假 runner）进行中时调用 `stop()` | 等它结束、结果写入后才关库 |
| `plugin/tests/` 下新文件 | 同一组快照和批次，分别经 HTTP 客户端和进程内客户端提交 | `source_events`、`chunks` 的内容和检查点相同 |
| 同上 | 数据库里已有某来源的检查点，进程内采集器启动 | 从检查点继续，不重复入库 |
| 同上 | 时间线条目带回合 ID | 插件采集器归一后的事件带同一个回合 ID |
| `plugin/tests/` 下新文件 | 插件服务端入口启动后执行清理函数，再启动一次 | 只有一个中心、一套定时器；第一次的端口和数据库已释放 |

**隔离验证**（结果写进汇报）：在隔离 daemon 上按路径安装插件，使用该隔离 daemon 自己的配置（临时数据库、测试端口）。确认插件状态为 running，测试端口上的 `/status` 和 `/mcp` 可用；`paseo plugin reload` 两次后仍只有一个实例；`paseo plugin logs` 没有错误。

### B3 数据库位置和首次启动

**目的**：新安装自动生成私有配置并只监听本机；用过的数据库缺失或身份不符时暂停中心，保留恢复依据。

**规则**

- `ServerConfig.dbPath` 改为可选。没配置时，路径为 `<state 目录>/paseo-task-manager/<serverId>/task-manager.db`。state 目录取 `$XDG_STATE_HOME`，没有就用 `~/.local/state`；Windows 用 `%LOCALAPPDATA%`。`runServer`（独立运行）仍然要求配置 `dbPath`。
- **私有配置**：每个 daemon 在 `$XDG_CONFIG_HOME/paseo-task-manager/<serverId>/config.json` 保存唯一配置，缺省配置根目录为 `~/.config`。初次生成 700 目录、600 文件、两个独立随机令牌、端口 7718、回环监听、空 collectors，不写 dbPath。之后沿用同一文件；设置页显示路径。显式配置未指定监听地址时监听所有网卡。
- **首次启动**：私有配置目录没有库身份记录、文件也不存在时，建目录（权限 700）和数据库（权限 600），执行迁移，在数据库里写一个随机的库 ID，并把库 ID 和路径连同记录时间原子写入配置旁的 `database.json`（600），位置独立于数据库目录。
- **之后启动**：原库不存在时停用中心，设置页显示路径，提供“已找回文件，重试”和“确认从零开始”。路径已被其他数据库占用时显示两份库的路径和 ID，只允许重试，由用户移走它或修改 dbPath。
- 配置了 `dbPath` 但它的上级目录不存在时，报错，不自动创建（外接盘没挂上时不能在别处建空库）。
- 路径不能在 Paseo 的 home 目录或插件安装目录里（插件现有的配置校验已有这一条，沿用）。
- 已有的库（配置了 `dbPath`、库里还没有库 ID）：第一次由插件打开时写入库 ID 并记录。

**测试**

| 用例 | 预期 |
|---|---|
| 没配置 `dbPath`、没有记录、文件不存在 | 在默认路径建库，目录 700、文件 600，记录里有库 ID 和路径 |
| 第二次启动，文件和记录一致 | 正常打开，不新建 |
| 记录里有库，文件不存在 | 不启动，状态里有原因和记录的路径 |
| 记录里有库，文件存在但库 ID 不同 | 拒绝启动，异库和身份记录原封不动，不提供“从零开始” |
| 用户选择"确认从零开始" | 新建库，记录更新为新的库 ID |
| 配置的 `dbPath` 上级目录不存在 | 报错，没有创建任何目录 |
| 配置的 `dbPath` 指向一份还没有库 ID 的已有库 | 打开，写入库 ID 并记录，数据不变 |
| 设置了 `XDG_STATE_HOME` | 默认路径在它下面 |
| 两个不同 serverId 的 daemon | 默认路径不同 |

### B8 换代重发不再存成新版本

**目的**：agent 被重新加载后，Paseo 的时间线换代，采集器会把旧事件重读一遍。抽查线上数据，这类重发的事件绝大多数只有时间戳不同，正文和工具信息完全一样，却被存成了新版本（`revision_review`）。它们占了数据库相当一部分空间，还会让回合索引和检索多做无用功。

**改动**（`src/server/ingest-repo.ts`）

- 判断是否重复时，比较除时间戳以外的内容（类型、条目类型、正文、截断信息、工具信息）。和已有版本只有时间戳不同时，算作重复，保留最早存下的时间戳，不插入新行，不产生 chunk。
- 现有的 `content_hash`（包含时间戳）和它的唯一约束不动。新增的比较只在找到已有版本时进行。
- 不清理库里已有的重复版本：它们被 chunk 和回合索引引用着，B2 会按规则清掉其中的工具详情。

**测试**：`tests/server/epoch-replay.test.ts`（已写好，是这个 ticket 的契约）。其中"不产生新 chunk"一条现在就通过，是回归保护；另外三条在修复前失败。

### B4 在设置里接入其他机器

**目的**：接入一台已经在 Paseo 里的机器，不用改配置文件，也不用在那台机器上装任何东西。

**设置页**（插件现有的设置页上扩展）列出三类机器：

| 机器的状态 | 怎么显示 | 操作 |
|---|---|---|
| 本机，或已登记在本机 daemon 上 | 名字、在线状态、最后同步时间 | "采集"开关（即现有的 `selectedHosts`） |
| app 里连着，但没登记在本机 daemon 上 | 名字和"未接入" | "接入"按钮 |
| 两边都没有 | 无 | 手填：连接地址和名字，"接入" |

- **仅在 app 连接的机器**：列出名字和“未接入”，点“接入”打开手填表单，预填名字。等 SDK 公开监听地址后再做一键接入。
- **手填**：地址可以是 `主机:端口`、SSH 地址，或对方用 `paseo daemon pair` 生成的配对链接。登记失败时显示 Paseo 返回的错误码。配对链接含密钥，插件设置和日志里都不留存。
- **默认不采集**：新登记的机器默认关闭"采集"。关掉"采集"只停止采集，不删除登记。
- **来源身份**：一台机器的来源 ID 和机器名，先按 serverId 找 `ingest_sources` 里已有的；没有就用 `paseo-<名字的 slug>` 和它的名字。

**测试**

| 用例 | 预期 |
|---|---|
| serverId 在 `ingest_sources` 里已有记录 | 沿用已有的来源 ID 和机器名 |
| 新的 serverId | 来源 ID 为 `paseo-<slug>`，机器名为它的名字 |
| 两台机器名字的 slug 相同 | 来源 ID 不冲突 |
| 新登记的机器 | 默认不在 `selectedHosts` 里 |
| 关掉某台机器的"采集" | 采集停止，没有调用删除登记的接口 |
| 手填配对链接后登记 | 插件设置和日志里没有这个链接 |

### B9 全局态势的两处修正

**目的**：上线后的实际输出暴露了两个问题。

1. **待处理的排序。** 现在按等待时间从长到短排，二十多天前的停滞提醒占满了篇幅，此刻正在等你的 agent 反而被省略。改为先按类别、类别内再按等待时间从长到短：agent 正在等你回答 → 待你确认的问题 → 等你处理的阻塞 → 停滞的项目和未推送的仓库 → 其他。
2. **盲区只列有问题的来源。** 状态正常的来源不逐条列出，只在末尾写"其余 N 个来源正常"。已退役的来源不算问题。

**测试**（`tests/context/read.test.ts`、`tests/mcp/read-tools.test.ts`）

| 用例 | 预期 |
|---|---|
| 一个 30 天前的停滞提醒和一个 5 分钟前开始等你的 agent | agent 排在前面 |
| 同一类别里两条 | 等得久的在前 |
| 三个来源，一个离线 | 盲区只列离线的那个，并写"其余 2 个来源正常" |
| 全部来源正常 | 盲区只有一行"N 个来源正常"和待摘要、拒摘的计数 |

### B1 经指针读原文

**目的**：B2 清掉工具详情之后，读者明确要看原文时，从 Paseo 重新读取。

**规则**

- 只有明确的读取会去 Paseo 取：`pm_read_raw`、`pm_get_turn` 里条目的正文、网页的证据抽屉。后台任务（整理员、阻塞复核）永远不去 Paseo 取。
- 取法：用插件的 daemon 连接（远端机器经 `hosts.client(serverId)`）找到这个 agent 的时间线，按事件的稳定标识（消息 ID 或工具调用 ID）翻页定位。时间线的代号和序号只作提示。每次读取有超时上限。
- **关闭主机采集**：停止从这台机器取回详情，显式读取也遵循此开关。返回“这台机器的采集已关闭，在设置里打开后可读取”和中心保留的概要。已在库中的内容照常提供。
- **已关闭的 agent**：读取会让它重新加载进 daemon。"读取已关闭 session 的内容"关闭时不去取，返回"中心已清除这段详情；读取需要重新加载这个 agent"，以及在 Paseo 里打开它的方式。打开时照常取。
- **取不到**：返回原因（机器离线、agent 已删除、会话文件已清理、时间线里找不到这一条），以及中心还保留的那一行概要。
- 取回的内容不写回数据库。
- 读取函数通过一个可选的依赖拿到"去上游取"的能力，只有插件模式下的明确读取路径会提供它。独立运行（`runServer`）时没有这个依赖，行为和现在一样。

**测试**（假的上游）

| 用例 | 预期 |
|---|---|
| 详情还在库里 | 不调用上游 |
| 详情已清除，agent 已加载 | 调用上游，返回取到的全文 |
| 详情已清除，agent 已关闭，设置关闭 | 不调用上游，返回说明 |
| 详情已清除，agent 已关闭，设置打开 | 调用上游 |
| 上游报错或超时 | 返回原因和一行概要，不抛错 |
| 后台任务读取同一条 | 不调用上游 |
| 取回之后 | 数据库里这一条仍是清除状态 |

### B2 工具详情的存储上限

**目的**：控制数据库体积，同时不丢对话。

**规则**

- 插件设置新增"工具详情存储上限"（host 范围），默认 2 GB。
- **计入的只有工具详情**：`source_events` 里工具调用的输入、输出和错误的字节数，所有版本都算。对话文本（用户和助手的消息）不计入，永远不清除。
- **超过上限时**：从最旧的开始清，直到用量不超过上限的 90%。清除时输入、输出写为空字符串，错误写为 null。事件 meta 保存清除时间和输入前 200 字，概要不计入用量。读层、回源和证据抽屉仅按清除标记判断。工具名、状态、退出码保留，回合大纲照常显示。
- **只清已处理的**：直接关联的所有 chunk 均已摘要、已跳过或已因拒摘隔离，才可清除。有且仅有一种例外：没有 chunk 映射的版本，在同一 session_key 和 event_key 下存在直接符合条件的版本，且输入、输出、错误逐字节相同时，也可清除。其他无映射事件保留。
- **何时运行**：入库后合并触发（不在入库事务里），以及上限调整后。分小批、短事务，不长时间占住数据库。
- **调小上限**：如果新上限低于当前用量，设置页先显示会清除多少、清除后详情最早保留到哪一天，用户确认后才保存。
- **清完仍超限**：停止清除，在全局态势的盲区里提示调高上限。
- **显示**：全局态势的盲区和设置页显示已用、上限，以及工具详情最早保留到哪一天。
- `chunks` 的文本本期不动。

**测试**

| 用例 | 预期 |
|---|---|
| 用量超过上限 | 最旧的工具详情被清除，用量降到上限的 90% 以下 |
| 同时有更旧的对话文本 | 对话文本不变，也不计入用量 |
| 最旧的一批还没摘要 | 跳过它们，清下一批已处理的 |
| 被拒摘隔离的事件 | 可以清除 |
| 清除后读回合 | 一行概要还在；读原文返回"已清除"，插件模式下走 B1 |
| 清除后搜索对话里的词 | 仍能搜到（对话文本没动） |
| 所有可清的都清完仍超限 | 停止，全局态势里有提示 |
| 上限调低到当前用量以下 | 先返回预估（字节数、最早保留日期），确认后才清除 |
| 用量在上限以内 | 什么都不做 |

### B10 来源可以标为已退役

**目的**：不再使用的来源（已退役的机器、已停用的 herdr 采集器）一直以"离线"出现在全局态势的盲区里，淹没真正的问题。现在没有办法标记"已退役"，第一期 B9 的"已退役的来源不算问题"因此没有生效。

**改动**

- 新迁移：`ingest_sources` 加 `retired_at`。
- 标为已退役和恢复：写入或清空 `retired_at`。
- 已退役的来源不再被当作问题：全局态势的盲区、来源覆盖、"来源断联"提醒都跳过它。盲区末尾单独计数，写"已退役 N 个"。
- 已退役的来源又上报了心跳或数据，说明它还在用：自动清除退役标记，按正常来源处理。
- 入口：插件设置页新增"来源"一节，列出所有来源（名称、类型、机器、最后同步时间、状态），每行有"标为已退役"或"恢复"。网页的来源覆盖页只读显示退役状态。

**测试**

| 用例 | 预期 |
|---|---|
| 一个离线的来源被标为已退役 | 盲区不再列出它，末尾计数"已退役 1 个" |
| 已退役的来源 | 不产生"来源断联"提醒 |
| 已退役的来源又上报心跳 | 退役标记被清除，之后离线会照常提醒 |
| 恢复一个已退役的来源 | 退役标记被清除 |
| 标记不存在的来源 | 报错，不改任何数据 |

### B11 整理员重跑同一批摘要不再产生重复条目

**背景**：整理员每次写操作单独提交，整批摘要要等整次运行结束才标为已整理。运行中途被结束（插件重载、daemon 重启、崩溃）后，下次重跑同一批摘要，会再建一份相同的决策和 todo（第一期汇报里已复现：从 1 条变 2 条）。

**改动**（只对 AI 写入者生效，即 actor 以 `ai:` 开头的操作；用户的操作不变）

- `record_decision`：同一项目里已有一条未删除的决策，规范化后的文字完全相同时，不新建，返回已有的 ID，不记事件。
- `upsert_todo` 不带 ID：同一项目里已有一条未删除的 todo，规范化后的标题完全相同时，当作对它的更新；字段都没变就什么都不做。返回它的 ID。
- 规范化：去掉首尾空白，连续空白合并成一个，英文不分大小写。
- 已删除的条目不参与比较，用户否决过的内容沿用现有的处理。

**测试**

| 用例 | 预期 |
|---|---|
| 第一期复现的场景：同一批摘要整理到一半被打断后重跑 | 决策和 todo 各只有 1 条 |
| AI 记录一条和已有决策只差空白和大小写的决策 | 返回已有的 ID，没有新事件 |
| 用户记录两条文字相同的决策 | 两条都建立 |
| AI 不带 ID 写一条标题相同、状态不同的 todo | 更新已有那条的状态 |
| 已有的相同决策已被删除 | AI 新建一条 |
